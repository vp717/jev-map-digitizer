Lesson 1 · Workflow engines · about 10 minutes

What re-runs when you change something?

Four tools can drive the map-digitizer pipeline. The clearest way to tell them apart is one question: when I change X, which steps run again? By the end of this lesson you can answer that for each tool and make the Q1 decision.

The job a workflow engine does

Our pipeline is a chain of steps, each turning files into other files:

render → groundtruth → split → tiles → detect → calibrate → evaluate → report
              legend → read-legend ↗

Run across every area × zoom × scale × k × method, that is hundreds of jobs. A workflow engine does three things for us:

  1. Expands the grid: turns "every method on every area" into concrete jobs.
  2. Decides what is stale: skips work whose inputs haven't changed, and redoes work whose inputs have.
  3. Orders the jobs: runs tiles only after split.

All four options handle ordering. They differ on the first two.

Three ways to decide "stale"

Make: file timestamps

Make rebuilds a file when one of its inputs has a newer modification time. It never looks at file contents. I checked this with GNU Make 4.4.1: after changing an input's contents but setting its timestamp back to the year 2000, make replied 'out.txt' is up to date. [manual]

Snakemake: several recorded triggers

By default Snakemake re-runs a job if any of five things changed: code, input, mtime, params, software-env. Its own help says this "guarantees that results are consistent with the workflow code and configuration" (checked in snakemake --help, v9.27.2). [CLI docs] So a changed parameter passed through a rule's params: re-runs that rule's jobs, even though no file changed.

DVC: content hashes

DVC "calculates a hash of file/dir contents to compare vs. previous versions", and records the hashes in dvc.lock. [DVC docs] A file rewritten with identical bytes doesn't count as changed. Each stage also lists the config keys it uses under params, and only those keys affect it. [dvc.yaml]

Your own Python runner: whatever you build

You decide the rule. That means writing change detection, the grid expansion and the ordering yourself, and testing them. Bugs there produce stale paper numbers without any error.

Worked example: change one number

You change the matching distance eval.match_px from 7 to 5 in the experiment config. Ideally only evaluate (and report) runs again. Nothing upstream, and no paid API calls.

Expanding the grid

Snakemake puts the grid in file paths. A wildcard such as {method} in an output path lets one rule cover every value. When you ask for a file, Snakemake reads the wildcard values off its path. [rules docs]

rule evaluate:
    input:  "out/runs/{method}/{area}/z{zoom}/predictions.gpkg"
    output: "out/runs/{method}/{area}/z{zoom}/metrics.json"
    params: match_px = config["eval"]["match_px"]
    shell:  "mapdig evaluate {input} --match-px {params.match_px} --out {output}"

rule all:   # ask for the whole grid
    input: expand("out/runs/{method}/{area}/z{zoom}/metrics.json",
                  method=METHODS, area=AREAS, zoom=ZOOMS)

DVC puts the grid in the stage definition. matrix creates one stage per combination; the docs' example gives "six stages, one for each combination of model and feature". [dvc.yaml]

stages:
  evaluate:
    matrix:
      method: [jev_loop, jev_verify, template, yolov8, yolso]
      area: [freiburg_centre, hinterzarten_rural]
    cmd: mapdig evaluate --method ${item.method} --area ${item.area}
    params: [eval.match_px]
    deps:  [out/runs/${item.method}/${item.area}/predictions.gpkg]
    outs:  [out/runs/${item.method}/${item.area}/metrics.json]

The difference: Snakemake works out which upstream job a file needs by matching paths, and you list only the final files you want. DVC's dependencies are written out explicitly in each templated stage, so every combination you ever run must be listed.

Two facts specific to this project

  • Containers. Snakemake's container: directive takes docker:// image URLs, but runs them through Apptainer, not the Docker engine. [deployment docs] We already use Docker Compose, so with either tool the step command would call docker compose run in the shell instead.
  • API answers. None of the four tools caches calls to Jev or Opus. That is our own content-addressed cache inside mapdig, whichever tool we choose.

DVC adds one thing Snakemake doesn't: it keeps outputs in its own cache and can dvc push them to remote storage. [repro docs] That overlaps with Q4 (where outputs and the API cache live).

Check yourself

Answer from memory first. Feedback is immediate.

1. In a Makefile where every rule lists config.yaml as an input, you change eval.match_px. What re-runs?

  1. Only the evaluation stage and its report
  2. Every stage that lists the config file
  3. Nothing, because no input file has changed
  4. Only stages whose output files are missing

Make only sees that config.yaml has a newer timestamp, so every rule that lists it is stale, including the expensive renders and API calls.

2. In Snakemake, match_px reaches the evaluate rule through params:. You change it and run snakemake. What happens?

  1. Nothing, until you add the force flag
  2. Every job in the whole workflow reruns
  3. Only the evaluate jobs rerun, by default
  4. Snakemake stops and asks you to confirm

params is one of the five default rerun triggers, so only jobs of rules whose params changed (and anything downstream of them) re-run.

3. In DVC, the render stage rewrites map.tif with identical bytes but a new timestamp. The tiles stage depends on it. What happens to tiles?

  1. Tiles are skipped since the hash matches
  2. Tiles rerun because the timestamp is newer
  3. Tiles rerun because the lock file changed
  4. DVC asks which stages you want rerun

DVC compares content hashes recorded in dvc.lock, not timestamps. Same bytes, same hash, nothing to do.

4. Which runtime does Snakemake's container: directive use to run a job?

  1. Docker Engine, through the docker compose file
  2. Podman, building from the local Dockerfile here
  3. No runtime at all; Snakemake ignores containers
  4. Apptainer, pulling from a docker:// image URL

The deployment docs run containers via Apptainer (--sdm apptainer), with docker:// as the preferred image source. For our Compose stack we'd call docker compose run from the shell command instead.

5. Which of these will none of the four tools cache for you?

  1. GeoTIFFs written out by the render stage
  2. Responses returned by Jev and Opus APIs
  3. GeoPackages written out by the diff stage
  4. Metrics files written out by evaluate stage

The engines track files that steps declare as outputs. Individual API responses happen inside a step, so the mapdig API cache has to handle them, whichever engine runs the pipeline.
